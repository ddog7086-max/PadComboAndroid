# v1.3 實測與增量迭代計畫

> 對象：`PadComboAndroid`（v1.2 已落地同向合併 / 重訪車道 / 固定法向 / 分軸累積 / 圓角 / 邊界夾取 / 箭頭回保）。
> 分離原則：語意層（`BeamSearchSolver` / `BoardEngine`）負責結算；渲染層（`RouteBoardView`）只負責怎麼畫。兩層互不吃回寫。
> 標記：【已確認】現行程式可對應；【推估】依程式脈絡推測，需實測；【待驗證】需真盤 / 對照原生結算才能定案。

## 1. v1.3「王」字水平帶分層規格與偽碼

### 1.1 適用情境（渲染層判定，不改路徑）
【已確認】同一 `row` 出現兩條以上水平折返段（上層來、下層回），局部直向穿插穿過這些水平帶。目的是讓上下水平層次靠垂直錯開顯示，而不是全部擠在同一條中心線上。

### 1.2 水平帶分組（在原始 `route` 上做，壓縮前）
- 邊 `eᵢ = (route[i], route[i+1])`：
  - 水平邊 `H`：`row` 相同；垂直邊 `V`：`col` 相同。
- 連續同 row 的水平邊組成一條**水平通過段（Pass）**；一條 Pass 對應該橫帶的一次通過。
- 依 `row` 歸入水平帶 `band[row]`；Pass 在帶內的先後順序＝`visitRank`（沿 route 從頭到尾編號）。

偽碼：

```text
function splitHorizontalPasses(route): Map<row, List<Pass>>
    runs = []
    i = 0
    while i < route.size - 1:
        a = route[i]; b = route[i+1]
        if sameRow(a, b):
            r = a.row
            startEdge = i
            while i < route.size-1
                  and sameRow(route[i], route[i+1])
                  and route[i].row == r:
                i++
            runs.add(Pass(row = r, edgeRange = [startEdge, i-1], rank = 次數編號))
        else:
            i++
    return runs.groupBy(row)
```

### 1.3 槽位分配（水平帶）
【已確認】沿用既有固定法向、對稱槽位架構；水平 Pass 的法向為 Y（垂直方向錯開）。

- 帶內通過數 `bandN = band[row].size`。
- 實體槽位上限 `laneCap = 3`；`activeN = min(bandN, laneCap)`。
- 槽位離中心距離對稱：
  - `activeN = 1`：slot = 0（中心線）
  - `activeN = 2`：slot ∈ {-1, +1}
  - `activeN = 3`：slot ∈ {-1, 0, +1}
- 槽距 `spacing = 0.11 · cellSize`（落在規格 0.10–0.12 cell 區間）。
- 單邊最大偏移封頂 `0.28 · cellSize`；超出壓縮 spacing，不把線推出珠心。
- `bandN > 3`：第 4 條及以後**不新增實體槽位**，複用最外槽，靠「後畫壓上」表達先後；不加中段步號、不畫複線。

偽碼：

```text
function horizontalSlot(rank, bandN, cell):
    activeN = min(bandN, 3)
    spacing = min(0.11 * cell, 0.28 * cell / max(activeN-1, 1))
    if activeN == 1: slot = 0
    elif activeN == 2: slot = if rank == 0 then -1 else +1
    else: slot = rankToCenterSlot(rank)   // -1,0,+1 對齊中間
    // 超額 rank 對應的槽壓回外槽，不給第四槽
    return slot * spacing
```

### 1.4 直向穿插邊（垂直）
- 垂直邊沿用現有 `edgeCount` 無向邊重訪統計，沿 X 法向開槽；不因水平帶分組而改動。
- 頂點偏移維持**分軸累積**：X 只取垂直鄰邊、Y 只取水平鄰邊；水平 Pass 的 Y 偏移不滲到垂直段。

### 1.5 與既有限制的銜接
- **封頂**：任一車道離中心線 ≤ 0.28 cell；計算後仍過 `clampPointToBoard`，`clipRect` 兜底。
- **終點箭頭保護**：最後一條邊若屬水平 Pass，終點的 Y 偏移在箭頭端點回退到接近珠心（箭頭不被帶出珠子）；箭頭最後畫，不被車道蓋住。
- **重訪統計時機**：`edgeCount`、Pass 分組、`visitRank` 全部在原始邊序列上算；同向合併只刪畫圖折點，不影響槽位與分層。
- **繪製順序**：單次中心線 → 水平 / 垂直外槽 → 內槽（後走壓上）→ 起點圓點 → 終點箭頭。

### 1.6 不改動的東西（語意層分離）
- 不依 `visitRank` 回頭調整搜尋偏好；不為了分層好看改動 path、禁止重訪或換序。
- 車道分層資訊只存在渲染副本；`SearchResult.path` 原樣回傳。

## 2. 實測檢核清單與對比指標

### 2.1 取樣盤面
【待驗證】準備 5–8 張固定真機盤面截圖，涵蓋：
- 短盤（≤8 步）：基線，確認無回歸。
- 中盤（9–14 步）：一般重訪。
- 長盤（15–20 步）：含水平折返 + 直向穿插的密集重疊（對標截圖 19 步 9 消）。
- 每張盤固定同一辨識結果、同一條搜尋路徑，v1.2 與 v1.3 各截一張對照圖。

### 2.2 視覺檢核（前後對照）
| 項目 | 檢查方式 | 通過標準 |
|---|---|---|
| 直線段 | 截圖比對同向連段 | 中間無斜折、無多餘小轉角；起終點位置不變 |
| 井字交叉 | 橫豎交叉局部 | 橫線 Y 錯位、豎線 X 錯位，交叉點不黏成一團 |
| 王字水平帶 | 同 row 多條折返 | 上下層可分辨先後；外槽不脫離珠心 |
| 邊界夾取 | 左右邊緣 / 底行 | 線與箭頭不進入珠外深啡邊界；底 row 4 不出界 |
| 終點箭頭 | 終點珠 | 箭頭貼最後一段方向，不被車道偏移推離 |
| 重訪可读性 | 15–20 步長盤 | 走向與終點可讀，無複線 / 灰管道 / 中段箭頭 |

### 2.3 渲染效能指標
【已確認】幾何在 `show()` 算一次，`onDraw` 復用 Paint/Path。
- 量測 `show()` 幾何構建耗時（邊統計、Pass 分組、槽位、合併折點）。
- 量測 `onDraw` 單幀耗時；長盤（20 格）下不得出現可見掉幀。
- 相同路徑重複回饋時不重算、不 `invalidate`。
- 記錄：峰值 `onDraw` ms、幾何構建 ms、每幀配置物件數。

### 2.4 Combo 結算對比
| 指標 | 來源 | 用途 |
|---|---|---|
| 預測 Combo（app 顯示） | `evaluatePath` → `predictedCombo` | 與實機結算比對 |
| 實機 Combo | 遊戲內實際消除結果 | 真值 |
| 第一波消除數 / 色數 | `chain.rounds[0]` | 視為可較高信心的已確認結果 |
| 第二波及以後 | `rounds[1..]` | 標為預測，需對照驗證 |
| 消除格數分色 | `clearStat` | 檢查是否有跨波次重複計數 |

## 3. Combo 自評偏高排查方向

### 3.1 現行結算流程（【已確認】程式事實）
- `applyDragPath`：手持珠沿路徑平移，終點填回手持珠（非逐段 swap）。
- `resolveChain`：`findClears` 找 ≥3 連橫 / 直 → 重力下落 → 頂部**隨機補珠** → 再判定，每輪 combo +1。
- `evaluatePath`：平移後跑 `resolveChain`，`totalCombo` 直接進評分（基礎 100/combo，高 combo 再加 60/combo）。

### 3.2 最可能的計算盲點（依機率排序）

**A. 補珠來源是隨機 RNG【推估 · 高機率】**
- `applyGravityAndRefill` 用 `Orb.ALL[rng.nextInt]` 補頂部空位；真機補珠來自固定轉珠佇列，離線無法預知。
- 後續波次的 Combo 是隨機樣本，同一路徑重跑可能得到不同 combo；評分容易選到「補珠剛好湊出連鎖」的高估路徑。
- 交叉驗證：同一盤同一條 path 連跑 N 次，記錄 `totalCombo` 分布；若方差 >0，即確認 RNG 不穩定。

**B. 第一波與後續波次信心混在一起【推估 · 高機率】**
- 第一波（平移後、未下落補珠前）消除可較高信心；第二波起依賴重力 + 補珠，屬預測。
- 現行把所有波次 combo 同權重計入評分與顯示，容易把投機連鎖算成穩定 combo。
- 交叉驗證：把 `rounds[0]` 與 `rounds[1..]` 分開記錄，對照真機哪一波是實際成立的。

**C. 重力 / 下落模型與實機差異【待驗證】**
- 需核對：非消除珠是否完整下落、頂部補珠位置、同色相鄰判定是否符合實機。
- 交叉驗證：固定一盤，手動重現下落後盤面，與 `nextBoard` 逐格比對。

**D. 消除格跨波次 / 交叉型重複計數【推估 · 中機率】**
- `findClears` 橫豎各掃一次取聯集，單格在同一輪只計一次；但需確認交叉形（L / T）同色格是否被正確歸入同一輪、未在後續輪次被殘留格重複算入。
- 交叉驗證：輸出每輪 `clearedCells` 清單，檢查格座標是否跨波次重複出現。

**E. 未建模的珠種狀態【待驗證】**
- 鎖珠、障礙珠、強化珠、心珠倍率、隊長主動技 / 隊長技倍率未納入；辨識誤判也會讓輸入盤面本身就錯。
- 交叉驗證：抽出自評與實機落差最大的幾張，先核對辨識六色是否正確，再排查結算。

**F. 評分放大誤差【推估 · 中機率】**
- combo 基礎 100 + 高 combo 加 60，等於高估一個 combo 的權重很高；結算偏高一點會被評分放大，beam 傾向選高投機路徑。
- 交叉驗證：臨時把後續波次 combo 降權，比對 beam 輸出路徑的實機 combo 是否更貼近。

### 3.3 交叉驗證步驟（建議順序）
1. **固定輸入**：把測試盤面離線存成 5×6 陣列，辨識結果不參與這輪對照，排除辨識干擾。
2. **重跑穩定性**：同一 path 跑 20 次 `resolveChain`，記錄 combo 與各輪消除格；方差不為 0 → 先處理補珠確定性。
3. **波次分離**：日誌輸出 wave1 combo / 消除色數、wave2+ 預測 combo；對照真機實際成立波次。
4. **重力逐格比對**：人工核對 `beforeBoard → nextBoard` 下落結果。
5. **對照原生 `libdropfield.so`**：在真機固定盤 + 固定路徑，截取遊戲實際 combo / 消除色數，與 app 預測逐波次對照（【待驗證】原生 so 行為無法從離線程式直接複製，只能黑盒對照）。
6. **回歸辨識**：結算合理後，再把辨識誤判納入比對。

### 3.4 落地建議（不動搜尋語意的前提下）
- 【待驗證】結算先提供「無補珠 / 固定種子補珠」模式：後續波次只作參考，不參與高權重評分。
- 顯示層可區分「第一波已成立」與「後續波次預測」，但此為 UI 呈現，不改 beam 決策，待實機真值確認後再調權重。
